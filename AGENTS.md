# Инструкции для агентов S.Center

## Назначение и зрелость

S.Center в этом workspace — frontend-прототип на HTML, CSS и JavaScript. Данные демонстрационные и исполняются в браузере. Не утверждайте наличие backend, долговременного хранения, совместной работы, ролей, прав, аудита, производственной безопасности или внешних интеграций без отдельной реализации и проверки.

## Источники истины

Для текущего состояния используйте в порядке приоритета: наблюдаемое поведение и проверки, исполняемый код, поддерживаемую текущую документацию. Для целевого состояния используйте явное решение пользователя, утверждённую целевую спецификацию и активный план. Транскрипции, скриншоты и исходные transfer-снимки являются evidence или историческим контекстом, но не заменяют актуальные текущие и целевые владельцы.

## Маршрут перед изменением

1. Определите наиболее узкую область по [реестру](./docs/context-governance/area-registry.json): при совпадении нескольких `scopePaths` выбирается самый длинный путь.
2. Откройте локальный индекс области и выберите маршрут по типу задачи; не читайте всё дерево документации.
3. Прочитайте владельца изменяемого факта, точный текущий исходник и проверку затронутого результата.
4. Для целевого изменения сопоставьте целевую спецификацию с текущим baseline; не описывайте изменение как реализованное до проверки.
5. Расширяйте контекст только для конкретного недостающего факта, зависимости или потребителя. Историческое evidence подключайте при проверке происхождения решения или конфликте владельцев.

## Повторяемое формирование контекста

- Перед изменением классифицируйте сведения как `current`, `target`, `transition`, `hypothesis`, `evidence` или `stale`.
- Для локальной задачи стартовый пакет состоит из применимых инструкций, локального индекса, одного владельца факта, точного evidence и проверки.
- Новая самостоятельная область получает локальный индекс, запись в реестре и ссылку из ближайшего родительского индекса. Пустые области и полный комплект документов по шаблону не создаются автоматически.
- Общий для нескольких областей факт переносится к ближайшему общему владельцу; потребители сохраняют локальное следствие и ссылку.
- Полный протокол, критерии выделения областей и матрица влияния находятся в [регламенте контекста](./docs/context-governance/README.md).

## Границы изменений

- Реализуйте согласованные изменения шахматки в `s-center-prototype`; не превращайте `digital-chessboard-transfer` в конкурирующую активную реализацию.
- `digital-chessboard-transfer` сохраняется как исходный снимок, пока его долговременные контракты и происхождение нужны проекту. При первом намеренном расхождении копий одновременно обновите технический baseline, архитектурную спецификацию и проверку синхронности.
- `component-library-transfer` сейчас является переносимым снимком и внешней зависимостью прототипа. Не добавляйте туда продуктовые правила S.Center. Изменение общего компонента должно сохранять его общий контракт, истории и переносимость либо сопровождаться явным решением о превращении каталога в поддерживаемый пакет S.Center.
- Не вводите новый framework, backend, зависимость или производственную гарантию без прямой команды пользователя.
- Не удаляйте и не перемещайте transfer-каталог до проверки runtime-потребителей, входящих ссылок, манифестов и переноса долговременных правил к их владельцам.

## Документация и прогресс

- Один долговременный факт имеет одного владельца; в остальных документах оставляйте локальное следствие и ссылку.
- Новое текущее поведение фиксируйте только после реализации и проверки. Согласованное, но не реализованное поведение остаётся целевым.
- Чекбокс плана отмечается выполненным только после прохождения критериев конкретного пункта; одновременно обновляются сводка прогресса и затронутый текущий baseline.
- Новый документ регистрируется у ближайшего индекса. Не создавайте пустые каталоги, дублирующие спецификации и временные документы без владельца и условия удаления.
- Новая область или перемещение существующей одновременно обновляет реестр, родительский и локальный индексы и автоматическую проверку маршрута.
- Используйте относительные ссылки. Не сохраняйте в документации пути к Temp, AppData, пользовательским каталогам, cache или внешним сессионным артефактам.
- После завершения плана перенесите долговременные результаты к постоянным владельцам и удалите временный план, если проект не требует отдельной истории.

## Делегирование подагентам

Каждая подзадача должна получить: цель, тип задачи, точную область чтения, точную область записи, запрещённые области, состояние `current` или `target`, авторитетные источники, ожидаемый результат, команды приёмки и известные нерешённые вопросы. Подагент не расширяет область молча.

Не назначайте нескольким агентам одновременное изменение общих индексов, архитектурной карты, проверочных скриптов или одних и тех же файлов. При отсутствии изолированных рабочих копий параллельные изменения допускаются только в непересекающихся областях; итоговую интеграцию и общие проверки выполняет один основной агент.

## Проверки

После изменения документации или межпакетной структуры запустите из корня:

```powershell
npm.cmd run check
```

Для узкой проверки допустимы:

```powershell
cd s-center-prototype
npm.cmd run check

cd ..\digital-chessboard-transfer
npm.cmd run check

cd ..\component-library-transfer
npm.cmd run verify
```

После изменения компонентной базы дополнительно соберите Storybook, если зависимости установлены. В итоговом отчёте укажите непроведённые проверки и причину.
