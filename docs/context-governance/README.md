# Управление контекстом S.Center

**Статус:** поддерживаемый регламент workspace  
**Область:** формирование, маршрутизация, расширение и жизненный цикл контекста  
**Зрелость:** применяется к frontend-прототипу; гарантии production-систем не предполагаются  
**Обновлять:** при появлении нового типа подсистемы, изменении источников истины, правил индексации или автоматических проверок

Этот документ определяет повторяемый процесс работы с контекстом S.Center. Он не содержит продуктовые правила отдельных функций. Цифровая шахматка является первой пилотной областью, но не владельцем общего стандарта.

## 1. Результат, который должен получать агент

Для каждой задачи агент должен собрать достаточный, но минимальный пакет источников:

1. применимые инструкции;
2. локальный индекс наиболее узкой затронутой области;
3. владельца изменяемого или проверяемого факта;
4. авторитетное evidence текущего либо целевого состояния;
5. команду или сценарий приёмки.

Чтение всех документов workspace, всей документации приложения или всех материалов встречи не является допустимым стартовым маршрутом для локальной задачи.

## 2. Термины

| Термин | Значение |
|---|---|
| Область контекста | Самостоятельная часть workspace с определённой границей, локальным индексом и владельцами сведений. |
| Локальный индекс | `README.md`, который направляет к минимальному пакету документов по типу задачи. |
| Владелец факта | Единственный документ, исполняемый контракт или источник, в котором хранится полное долговременное правило. |
| Стартовый пакет | Источники, которые читаются до расширения контекста. |
| Расширение контекста | Подключение дополнительного владельца для конкретного недостающего факта или границы. |
| Evidence | Транскрипция, кадр, аудит, исторический снимок или иной материал, подтверждающий происхождение или состояние, но не заменяющий поддерживаемого владельца. |
| Current | Подтверждённое текущее поведение. |
| Target | Согласованное целевое поведение, ещё не обязательно реализованное. |
| Transition | Временный план перехода и подтверждённый прогресс. |

## 3. Где находится контекст

- Корень workspace хранит только общие инструкции, архитектуру, реестр областей и маршруты.
- Контекст приложения хранится внутри его документационной области.
- Контекст функционального блока хранится у ближайшего локального владельца этого блока.
- Общий компонент хранит публичный кодовый контракт в компонентной базе; продуктовая роль компонента остаётся в интерфейсной карте потребителя.
- Межфункциональный сценарий создаётся у ближайшего общего владельца участвующих областей и ссылается на их локальные контракты.
- Исторические материалы остаются evidence и не входят в обычный стартовый пакет.

Единая корневая папка с копиями всей продуктовой информации не создаётся.

## 4. Реестр и выбор области

[Машиночитаемый реестр](./area-registry.json) связывает существующие пути workspace с локальными индексами. Для затронутого пути выбирается запись с наиболее длинным совпавшим `scopePath`. Поэтому дочерняя функция имеет приоритет над приложением, а приложение — над workspace.

Если задача названа функционально и ещё не содержит пути:

1. используйте корневой [индекс документации](../README.md);
2. найдите область по названию и назначению;
3. подтвердите границу через её локальный индекс;
4. только затем открывайте владельцев фактов.

Если ни одна специализированная запись не подходит, используется ближайшая родительская область. Создание новой области не является автоматическим следствием неизвестного термина.

## 5. Классификация задачи и стартовые маршруты

| Тип задачи | Стартовый пакет | Расширять только когда |
|---|---|---|
| Проверить текущее поведение | Локальный индекс, current-владелец, точный код или runtime, проверка | Результат пересекает границу другой области. |
| Сформулировать целевое правило | Подтверждённое решение, target-владелец, текущий baseline | Изменяется зависимость, потребитель или общая сущность. |
| Реализовать корректировку | Активный пункт плана, target-владелец правила, current-baseline, точный исходник и проверка | Возникает именованная зависимость или неизвестный контракт. |
| Аудировать соответствие | Target, current, наблюдаемый результат или код и критерии приёмки | Для расхождения требуется доказать происхождение решения. |
| Изменить общий компонент | Публичный контракт компонента, реализация, stories/проверка | Продуктовый потребитель меняет назначение или поведение компонента. |
| Изменить структуру или владельца | Архитектура workspace, регламент контекста, входящие ссылки, индексы и проверки | Обнаружен runtime-потребитель, генератор или дочерний контракт. |
| Проверить решение встречи | Поддерживаемый target-владелец и конкретное evidence | Поддерживаемые владельцы противоречат друг другу или не фиксируют решение. |
| Добавить новую область | Этот регламент, шаблон сегмента, родительский индекс и реальные источники новой области | Появляется общая сущность, межфункциональный поток или отдельная зрелость. |

## 6. Контролируемое расширение

Перед чтением дополнительного документа агент должен уметь назвать:

```text
Недостающий факт:
Добавляемый источник:
Почему именно он владеет или подтверждает факт:
Какая секция или проверка нужна:
```

Расширение прекращается, когда факт установлен. Совпадение слов в документах не является основанием загружать их все.

## 7. Владение и отсутствие дублирования

Для долговременного правила выбирается один первичный владелец. Другие документы могут содержать только:

- локальное следствие правила;
- идентификатор требования или области;
- ссылку на владельца;
- статус покрытия, если документ владеет трассировкой или проверкой.

Типовые владельцы:

| Сведение | Владелец |
|---|---|
| Наблюдаемое текущее поведение | Runtime, код, исполняемый контракт и current-baseline области |
| Согласованное целевое поведение | Функциональная или архитектурная target-спецификация |
| Очередь перехода и прогресс | Временный implementation plan |
| Предметные сущности и отношения | Локальная либо общая domain model |
| Роль интерфейсной области и связи компонентов | Interface map функционального блока |
| Связь требований с кодом и проверками | Traceability matrix без копирования полного текста требований |
| Публичная механика общего компонента | Компонентная база, публичный entry point и stories |
| Происхождение решения | Evidence; только для проверки или разрешения конфликта |

## 8. Когда создавать новую область

Новая область создаётся, если подтверждено хотя бы одно условие:

- самостоятельный пользовательский результат и граница интерфейса;
- отдельный набор продуктовых правил или состояний;
- собственный current-baseline или lifecycle;
- несколько связанных документов с единым владельцем;
- отдельная зрелость, например prototype UI и production API;
- самостоятельная проверка или команда приёмки.

Не создавайте область только из-за одного небольшого документа, будущей идеи, временного исследования или повторяющегося термина.

### Процедура регистрации

1. Определить назначение, границу и родителя области.
2. Определить current/target-зрелость и авторитетные источники.
3. Создать минимальный локальный `README.md` по [шаблону](./context-segment-template.md).
4. Добавлять только документы с отдельным владельцем и событием обновления.
5. Зарегистрировать существующие `scopePaths`, индекс и команды проверки в `area-registry.json`.
6. Добавить ссылку из ближайшего родительского индекса.
7. Запустить `npm.cmd run check:docs`, затем требуемые проверки области.

## 9. Рост и перенос владельца

### Новая независимая функция

Функция получает соседнюю локальную область. Корневой маршрут меняется только тогда, когда функция является новой самостоятельной областью уровня workspace.

### Общая сущность нескольких функций

Если один предметный факт используется несколькими областями, его полный контракт переносится к ближайшему общему владельцу. Локальные модели сохраняют только свои ограничения и ссылку.

### Межфункциональный сценарий

Отдельный flow-владелец создаётся, когда пользовательский результат проходит через две или более независимые области. Он фиксирует участников, передаваемое состояние и итог, но не копирует внутренние спецификации участников.

### Новое приложение, пакет или сервис

Самостоятельный runtime получает собственный индекс, maturity, источники истины и проверки. Production-гарантии одной подсистемы не переносятся на prototype-подсистему по соседству.

### Изменение физической структуры

Каталоги `features`, `flows`, `shared`, `apps` или `packages` создаются только после появления реальных сущностей, которые требуют такой группировки. Реестр и маршруты обновляются в той же задаче, что перемещение.

## 10. Повторяемый протокол изменения

Для каждого изменения документации или функциональности:

1. **Разрешение области:** определить наиболее узкий индекс через реестр.
2. **Классификация состояния:** current, target, hypothesis, transition, evidence или stale.
3. **Выбор владельца:** установить единственный документ или исполняемый контракт изменяемого факта.
4. **Стартовый пакет:** прочитать владельца, точное evidence и проверку.
5. **Анализ влияния:** проверить только реально затронутых потребителей.
6. **Изменение:** не описывать target как current до проверки реализации.
7. **Синхронизация:** обновить локальный индекс, baseline, план или матрицу только по их ответственности.
8. **Проверка:** выполнить структурные и предметные команды.
9. **Очистка:** удалить stale-ссылки, завершённый временный контекст и потерявшие владельца assets.

## 11. Матрица влияния

| Изменение | Проверить |
|---|---|
| Видимая структура | Interface map, target/current UI-владелец, visual acceptance |
| Действие пользователя | Поведенческий контракт, затронутый flow, acceptance |
| Состояние или расчёт | Domain model, потребители, baseline и тесты |
| Общий компонент | Публичный контракт, stories, продуктовые карты потребителей |
| Реализация без изменения контракта | Current-baseline и implementation map; target не переписывается |
| Новая область | Реестр, локальный и родительский индексы, проверки |
| Перемещение или удаление | Входящие ссылки, runtime-потребители, карты, проверки и assets |
| Завершение плана | Перенос долговременных правил к владельцам и удаление временного плана |

## 12. Автоматическая проверка и её пределы

Корневая команда `npm.cmd run check:docs` проверяет реестр, существование областей и индексов, родительские маршруты, уникальность идентификаторов, корректность иерархии и переносимость ссылок. Полная `npm.cmd run check` дополнительно запускает проверки пакетов и runtime-контрактов.

Автоматическая проверка не может подтвердить смысловую точность решения, визуальное соответствие, отсутствие скрытого продуктового дублирования или корректность классификации current/target. Эти свойства проверяются по владельцам и evidence во время задачи.

## 13. Критерии корректной маршрутизации

- локальная задача находит область не более чем через корневой и один локальный индекс;
- стартовый пакет не требует чтения соседней области без установленной зависимости;
- транскрипции и скриншоты не являются обязательным контекстом реализации;
- новый раздел регистрируется без переписывания правил существующих областей;
- общий факт имеет одного владельца на ближайшем общем уровне;
- все зарегистрированные пути, индексы и родительские ссылки проходят автоматическую проверку;
- удаление или перенос не оставляет активных ссылок и конкурирующих владельцев.
