# Готовое поручение coding agent

**Состояние:** операционная инструкция; не создаёт требований сверх связанных нормативных документов

**Режим данного готового поручения:** максимальная близость к текущему прототипу при приоритете нормативного результата

Ниже приведён текст, который можно передать coding agent вместе с этой директорией и доступом к целевому frontend-репозиторию.

## Поручение

Реализуй вложенную вертикальную прокрутку матрицы, плавную передачу движения общему правому контейнеру и согласованную фиксацию областей раскрытой работы.

Авторитетный контекст задачи:

1. [interface-roles-and-relations.md](./interface-roles-and-relations.md) — семантические роли и пространственные отношения;
2. [behavior-and-algorithm.md](./behavior-and-algorithm.md) — нормативные требования и эталонная алгоритмическая модель;
3. [acceptance-scenarios.md](./acceptance-scenarios.md) — обязательная программа проверки.

[prototype-verification.md](./prototype-verification.md) показывает, как контракт сопоставлен с исходным прототипом. Это ненормативное evidence: оно помогает понять глубину проверки, но не заменяет реализацию и повторную приёмку в целевом проекте.

Для этого готового поручения дополнительно используй [prototype-kinematics-reference.md](./prototype-kinematics-reference.md) и его [машиночитаемые векторы](./prototype-kinematics-vectors.json). Они задают исходные параметры fidelity-режима, но не отменяют приоритет нормативных требований и фактической геометрии целевой дизайн-системы. Если конкретная downstream-задача требует только контрактного соответствия, владелец проекта должен явно снять fidelity-режим.

Эти документы технологически нейтральны. Не ищи в них названия реальных компонентов, классы или DOM `id`: их нужно определить в целевом проекте самостоятельно.

## Обязательный порядок работы

1. Прочитай три нормативных документа полностью, выдели все требования с идентификаторами и просмотри текущую контрольную точку прототипа как evidence. Определи, требует ли поручение контрактного соответствия или максимальной близости к прототипу.
2. Исследуй целевой репозиторий, инструкции проекта, существующие компоненты, scroll-контейнеры, стили, lifecycle и штатные команды проверки.
3. Составь рабочее сопоставление ролей `UI-Rxx` с фактическими компонентами или элементами. Не изменяй документацию пакета ради названий целевого проекта.
4. Проверь, кто уже владеет нативным wheel, overflow, smooth scroll, sticky и scroll anchoring. Не добавляй второго владельца поверх существующего механизма.
5. Выбери реализацию в рамках архитектуры проекта. Предпочитай публичный API компонента и продуктовую обёртку; не изменяй внутренности общей библиотеки без явного разрешения.
6. Реализуй требования. Не копируй структуру неизвестного исходного прототипа и не вводи другой framework или зависимость без разрешения проекта. В fidelity-режиме перенеси reference-векторы в штатный test runner либо создай эквивалентные parameterized tests; пиксельную геометрию адаптируй к фактическим размерам компонентов.
7. Выполни все применимые сценарии `AC-*` в поддерживаемых desktop-браузерах. Проверь console errors и измеримые позиции scroll-контейнеров; арифметические reference-векторы не заменяют Browser QA.
8. Исправляй дефекты до прохождения критериев либо зафиксируй точный технический блокер, который нельзя устранить в разрешённой области.
9. В финальном отчёте перечисли сопоставление ролей, изменённые файлы, архитектурное решение, проверки, evidence и оставшиеся ограничения. В fidelity-режиме отдельно перечисли отклонения от reference-профиля и причину каждого.

## Требования к автономности

- Сначала ищи ответы в целевом репозитории, публичном API его компонентов и исполняемом интерфейсе.
- Не требуй от frontend-разработчика вручную переносить классы, ID или дописывать данный пакет.
- Задавай вопрос только если недостающий выбор materially меняет продуктовый результат и его невозможно установить из предоставленного контракта или целевого проекта.
- Если библиотечный компонент не предоставляет нужный scroll-host, исследуй предусмотренную композицию или локальную обёртку. Не объявляй библиотеку непригодной без проверки её публичного контракта.
- Не утверждай прохождение сценария без браузерного evidence.

## Критерий завершения

Работа завершена только когда:

- реализованы все применимые нормативные требования;
- пройдены все применимые `AC-*` без console errors;
- на границе прокрутка продолжается без движения курсора;
- при внутреннем движении внешний scrollbar не дёргается в обратную сторону;
- sticky-группа сохраняет синхронность и корректно отпускается;
- полноэкранная матрица не изменяет скрытый внешний scroll и восстанавливает собственную позицию;
- очистка lifecycle подтверждена;
- итоговый отчёт содержит воспроизводимое evidence.

Если был выбран fidelity-режим, дополнительно должны проходить перенесённые reference-векторы либо их документированные эквиваленты; все отклонения от параметров прототипа должны быть объяснены и подтверждены браузерной проверкой.

Успешная сборка без Browser QA не является завершением задачи.
