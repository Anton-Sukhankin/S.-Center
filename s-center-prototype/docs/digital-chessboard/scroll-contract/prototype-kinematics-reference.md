# Эталонный профиль кинематики исходного прототипа

**Состояние:** текущий ненормативный reference profile; не создаёт требований целевой реализации  
**Снимок реализации:** S.Center prototype, проверено 29.08.2026  
**Назначение:** дать coding agent точные параметры и последовательность текущей реализации, когда требуется максимально близко воспроизвести ощущение прокрутки прототипа  
**Нормативные владельцы результата:** [поведение и алгоритмическая модель](./behavior-and-algorithm.md), [сценарии приёмки](./acceptance-scenarios.md)  
**Машиночитаемое приложение:** [prototype-kinematics-vectors.json](./prototype-kinematics-vectors.json)

## 1. Граница и приоритет

Нормативный scroll-контракт отвечает, **какой наблюдаемый результат должен быть получен**. Этот профиль отвечает, **какими числовыми параметрами и фазами такой результат сейчас достигается в прототипе**.

| Режим передачи | Обязательный контекст | Как трактовать профиль |
|---|---|---|
| Контрактное соответствие | Три нормативных документа пакета | Не требуется; целевой проект выбирает собственную кинематику и проходит все `AC-*` |
| Максимальная близость к прототипу | Нормативные документы, этот профиль и JSON-векторы | Использовать как исходную настройку, затем проверить в браузере целевого проекта |

При конфликте приоритет имеют нормативные требования и измеримый результат в поддерживаемых браузерах целевого проекта. Отклонение от профиля допустимо, если оно нужно архитектуре, accessibility, производительности или браузерной совместимости и зафиксировано в отчёте. Отклонение не освобождает от прохождения `AC-*`.

Текущий JS/CSS и browser-тесты прототипа являются источниками current-фактов. Автоматическая проверка сравнивает значения этого профиля с исходниками; ручное изменение JSON без соответствующего изменения реализации должно завершаться ошибкой.

| Ключ JSON | Текущее значение | Роль | Переносимость |
|---|---:|---|---|

| `maxFrameElapsedMs` | `48 ms` | Ограничение скачка после задержки main thread | Стартовая настройка |

| `maximumVisibleFloorRows` | `15` | Текущая высота внутреннего viewport | Продуктовый инвариант видимой композиции |

| `prototypeMatrixHeaderHeightPx` | `34 px` | Текущая CSS-геометрия | Только reference текущей верстки |
| `prototypeVisibleFloorRowsHeightPx` | `675 px` | `15 × 45 px` | Производная текущей верстки |

Для `WheelEvent.DOM_DELTA_PAGE` отдельной константы нет: текущее правило всегда использует `deltaY × clientHeight(UI-R01)` и тем самым зависит от фактической высоты внешнего scroll-host.

В целевой системе число строк и условие прекращения фиксации сохраняются согласно нормативному контракту. Значения `45`, `34`, `675` и `8 px` нельзя жёстко переносить, если реальная дизайн-система задаёт другую геометрию: вычисления должны использовать фактические размеры.

## 3. Нормализация wheel-дельты

Для исходного события `(deltaY, deltaMode)` текущий профиль вычисляет вертикальную дельту `D`:

```text
deltaMode = PIXEL (0): D = deltaY
deltaMode = LINE  (1): D = deltaY × 16
deltaMode = PAGE  (2): D = deltaY × clientHeight(UI-R01)
```

Вертикальный маршрутизатор не перехватывает жест, если нажат `Ctrl`, нажат `Shift`, вертикальная составляющая практически равна нулю, owner матрицы не определён либо активна полноэкранная поверхность. В обычном диагональном событии оси декомпозируются: нормализованный `deltaX` изменяет `UI-R10.scrollLeft`, а нормализованный `deltaY` проходит inline-маршрутизацию независимо от соотношения модулей. В fullscreen нативная прокрутка `UI-R10` остаётся изолированной и не передаёт остаток скрытому `UI-R01`.

## 4. Профиль фаз inline-маршрутизации

Один cancelable вертикальный жест проходит следующие фазы в указанном порядке:

1. Определить устойчивого владельца жеста по `composedPath()` и timeout 180 ms.
2. Отсечь модифицированные и преимущественно горизонтальные жесты.
3. При fullscreen отменить inline-анимацию и оставить событие нативному владельцу.
4. Нормализовать `deltaY` в пиксели.
5. Для non-cancelable события дать браузеру выполнить нативное движение, на следующем animation frame измерить фактически пройденное матрицей и внешним контейнером расстояние, а только однонаправленный остаток поставить в общую очередь.
6. Для cancelable события вызвать `preventDefault()` и добавить дельту в единственную очередь движения.
7. При движении вверх сначала погасить расстояние, необходимое для выравнивания заголовка раскрытой работы с верхней sticky-границей (`outerLeadTarget`).
8. Оставшуюся отрицательную дельту распределить между подъёмом матрицы и уменьшением sticky-растяжения пропорционально доступным расстояниям.
9. Передать матрице доступную часть оставшейся дельты по inner-first правилу.
10. Передать внешний остаток `UI-R01`, ограничив обе цели реальными диапазонами scroll.
11. На каждом animation frame двигать цели в порядке `outer lead → matrix + coupled outer → final outer`, синхронно пересчитывая sticky-слои при фактическом движении внешнего контейнера.

Новая дельта того же направления накапливается в текущих target. Смена направления сбрасывает targets в фактические позиции, заново измеряет upward alignment и начинает новую фазу без инерционного продолжения в прежнюю сторону. Смена matrix/outer owner отменяет предыдущую очередь и создаёт новую.

## 5. Сглаживание и точное завершение

Для прошедшего времени кадра `dt`:

```text
elapsed = firstFrame ? 16 : clamp(dt, 1, 48)
factor  = 1 − exp(−elapsed / 65)
```

Позиция одной оси обновляется так:

```text
distance = target − current
next = |distance| ≤ 4 ? target : current + distance × factor
```

Для `elapsed = 16 ms` фактор равен приблизительно `0.2181980615483914`; для `48 ms` и любого большего интервала после clamp — `0.5221514981489528`. После попадания в диапазон 4 px устанавливается точный target, поэтому дробный хвост не должен поддерживать бесконечную анимацию.

При внешнем нативном изменении scroll-позиции текущие targets согласуются только в направлении активного движения: при движении вниз они не могут стать меньше фактических значений, при движении вверх — больше. Это предотвращает визуальный откат scrollbar.

## 6. Совместный подъём матрицы и sticky-группы

Для отрицательной дельты после выравнивания:

```text
matrixCapacity    = текущий matrix target над верхней границей
expansionCapacity = outer coupled target − upward expansion target
coupledCapacity   = matrixCapacity + expansionCapacity
coupledDistance   = min(−delta, coupledCapacity)
matrixDistance    = coupledDistance × matrixCapacity / coupledCapacity
expansionDistance = coupledDistance − matrixDistance
remainingDelta    = delta + coupledDistance
```

Совместная фаза применяется только когда обе capacity положительны. Поэтому сумма фактического подъёма матрицы и уменьшения sticky-растяжения соответствует потреблённой части wheel-дельты, а оставшееся расстояние продолжает обычную inner-first маршрутизацию.

## 7. Sticky-геометрия и восстановление позиции

Максимальный sticky-сдвиг текущая реализация получает из фактической геометрии:

```text
visibleFloorHeight = matrixViewportHeight − matrixHeaderHeight
minimumVisibleFloorHeight = 8 × floorRowHeight
maxStickyShift = max(0, visibleFloorHeight − minimumVisibleFloorHeight)
```

При текущих размерах `709 − 34 − 8 × 45 = 315 px`. Если viewport содержит только header и восемь строк (`394 px`), максимальный сдвиг равен нулю. Header аккордеона, легенда и matrix header получают один и тот же нормализованный transform.

Позиция матрицы хранится по составному ключу `project : object/tree node : period : work`. Если позиции ещё нет или она была сохранена не дальше 1 px от нижнего края, после изменения геометрии устанавливается новый maximum. Иначе восстанавливается сохранённое значение, ограниченное новым диапазоном. Fullscreen использует ту же позицию матрицы, но сохраняет и восстанавливает внешний scroll независимо.

## 8. Машиночитаемые векторы

[JSON-векторы](./prototype-kinematics-vectors.json) фиксируют примеры нормализации, inner-first передачи, совместного подъёма, frame factor, settle, sticky-предела, timeout owner и восстановления позиции. Они являются исполняемым reference, а не отдельным источником продуктовых требований.

Проверка `npm.cmd run check`:

- валидирует структуру и результат каждого вектора;
- сопоставляет числовые константы JSON с текущими JS/CSS;
- проверяет, что README, инструкция агента и checkpoint маршрутизируют этот профиль;
- завершает работу ошибкой при рассинхронизации.

Downstream-агент в режиме максимальной близости переносит векторы в штатный test runner целевого проекта либо реализует эквивалентные parameterized tests. Он должен отдельно выполнить нормативные браузерные сценарии: арифметические векторы не доказывают корректность DOM, event lifecycle, реального wheel и визуальной синхронности.

## 9. Условия пересмотра

Профиль и JSON заменяются согласованно при изменении любой константы, порядка фаз, формулы сглаживания, способа накопления targets, пропорции coupled-движения, owner timeout, sticky-геометрии или восстановления позиции. Изменение только нормативного результата не должно автоматически переписывать current-профиль до изменения и проверки прототипа.
