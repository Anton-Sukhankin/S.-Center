# Регламент повторного аудита цифровой шахматки

**Статус:** поддерживаемая методика независимой проверки  
**Последнее выполнение:** [текущая контрольная точка на 29.08.2026](../quality/digital-chessboard-current-audit/README.md)  
**Область:** frontend-прототип цифровой шахматки, его публичные компонентные зависимости и документационная трассировка  
**Не входит:** исправление найденных дефектов, backend, persistence, production-security и полный сертификационный accessibility-аудит

Регламент описывает повторяемую проверку и не является владельцем продуктовых требований. Целевое поведение берётся из [functional-context.md](./functional-context.md), текущее — из наблюдаемого поведения, исполняемого кода и [technical-baseline.md](./technical-baseline.md), переходные задачи — из [implementation-plan.md](./implementation-plan.md). Транскрипции и старые кадры используются только для проверки происхождения спорного решения.

## 1. Условия независимости

1. Аудитор начинает с локального индекса и названных владельцев, а не с истории чата.
2. Проверяемая ревизия, dirty-файлы, команды и ограничения фиксируются до вывода.
3. Аудит не меняет интерфейс и функциональность. Документальные противоречия можно синхронизировать отдельно; implementation-findings получают собственные пункты плана.
4. Выполнение аудита и отсутствие замечаний — разные состояния: пункт проверки может быть закрыт при наличии открытых findings.
5. Текущий checkpoint заменяется при следующем эквивалентном аудите; сессионные пути и append-only журнал не являются поддерживаемым контекстом.

## 3. Порядок выполнения

### A. Состояние и трассируемость

1. Зафиксировать ревизию, локальные изменения и доступные команды.
2. Сопоставить target, current и transition; не выводить требования из устаревшего evidence.
3. Проверить requirement IDs, владельцев, ссылки и доказательства выполненных чекбоксов.

### B. Статика, данные и компоненты

1. Проверить отсутствие продуктового использования `Bulk Action Bar`, `selectionMode: multiple`, календарного фильтра, сравнения и лейбла «Последовательность».
2. Проверить видимые planned-карточки сводки и отсутствие неподтверждённой аналитики.
3. Проверить семантическую принадлежность работ группе и календарную валидность всех дат.
4. Проверить публичные экспорты и stories `Chessboard`, `Menu`, `Tooltip`, `Accordion`, `Card` и связанных примитивов.

### C. Browser, responsive и accessibility smoke

1. Пройти контексты дерева, group picker, аккордеоны, ячейки, меню, tooltip и fullscreen.
2. Проверить закрытие overlays, focus management, `Escape`, отсутствие duplicate IDs и console errors.
3. Проверить viewports 1440, 1280 и 1024 px; page overflow недопустим, matrix overflow должен оставаться локальным.
4. Проверить доступные имена, роли, `aria-expanded`, `aria-selected`, focus-visible и независимость семантики от одного цвета.

### D. Автоматические команды

Из корня workspace:

```powershell
npm.cmd run check
```

Дополнительно для механики и общей компонентной базы:

```powershell
cd s-center-prototype
npm.cmd run test:scroll-contract

cd ..\component-library-transfer
npm.cmd run verify
npm.cmd run build-storybook
```

## 4. Формат результата

Текущая контрольная точка должна содержать:

- проверяемую дату и scope;
- сводку `PASS / FAIL / BLOCKED / NEEDS DECISION` по матрице;
- findings с приоритетом, владельцем и точной маршрутизацией;
- выполненные команды и непроведённые проверки с причиной;
- только значимое visual evidence по относительным путям внутри проекта;
- явное отделение дефекта реализации от ограничения прототипа и отсутствующего продуктового решения;
- решение по статусу задачи аудита и отдельный статус каждого finding.

Аудит считается выполненным, когда вся доступная область пройдена, ограничения зарегистрированы, а каждый finding передан владельцу. Полное принятие реализации возможно только при отсутствии открытых `FAIL` и `BLOCKED` либо после явного продуктового решения по ним.
