# План аудита корректировок после встречи 25.08.2026

**Статус:** подготовлен, аудит не запущен  
**Условие запуска:** отдельная команда пользователя после внесения корректировок в текущем диалоге  
**Проверяемая очередь:** [implementation-plan.md](./implementation-plan.md#дополнительные-корректировки-по-встрече-25082026)  
**Evidence требований:** [meeting-2026-08-25-analysis.md](./meeting-2026-08-25-analysis.md)  
**Текущее состояние до изменений:** [technical-baseline.md](./technical-baseline.md)

## 1. Цель и границы

Аудит должен доказать не только визуальное наличие элементов, но и соответствие данных, поведения, компонентных контрактов и состояния дерева решениям встречи. Результатом будет таблица `требование → код → автоматическая проверка → browser evidence → итог` с одним из статусов: `PASS`, `FAIL`, `BLOCKED`, `NEEDS DECISION`.

Аудит не подтверждает backend, долговременное хранение, реальные логины, роли, права, конкурентное редактирование или производственный audit trail. Если UI истории изменения использует демонстрационные данные, это должно быть явно отмечено.

## 2. Предусловия запуска

- Пользователь явно дал команду начать аудит.
- Все заявленные корректировки внесены или помечены разработчиком как намеренно отложенные.
- Активный план и `technical-baseline.md` синхронизированы с кодом.
- Прототип и Storybook запускаются локально; порты фиксируются в отчёте, а не в постоянной спецификации.
- Известна ревизия кода или снимок рабочей директории, который проверяется.

## 4. Порядок аудита

### Этап A. Состояние и трассируемость

1. Зафиксировать проверяемую ревизию, dirty-файлы и команды запуска.
2. Сопоставить каждый follow-up пункт плана с изменёнными файлами и тестом.
3. Проверить, что выполненные чекбоксы имеют доказательство, а отложенные решения не выданы за реализованные.

### Этап B. Статический и компонентный аудит

1. Проверить отсутствие продуктового использования `Bulk Action Bar`, `selectionMode: multiple`, карточек «План», «Отклонение», «Обновлено» и устаревшего лейбла «Последовательность».
2. Проверить публичные экспорты `Chessboard`, `Menu`/`Select`, `Tooltip`, `Accordion`, `Card` и связанные stories.
3. Проверить состояния компонентов: default, hover, focus-visible, selected, disabled, open/closed, loading/empty при наличии контракта.
4. Проверить, что продуктовая семантика статусов и формулы не перенесены в общий пакет.

### Этап C. Функциональный browser QA

1. Выбрать проект, очередь и объект; проверить доступность вкладки и отсутствие неявного fallback.
2. Пройти модальный выбор группы, поиск, radio-выбор, подтверждение и prev/next навигацию.
3. Проверить свёрнутые и раскрытые работы, длинные названия, даты, готовность и завершённое состояние.
4. Для каждой из пяти семантик ячейки открыть dropdown, выбрать значение и проверить визуальный результат.
5. Проверить закрытие dropdown по выбору, Escape, клику снаружи и смене аккордеона.
6. Проверить tooltip мышью и клавиатурным фокусом, включая длинный логин и границы viewport.
7. Проверить дома с различной геометрией, включая разную этажность секций и горизонтальное переполнение.

### Этап D. Accessibility и responsive

1. Пройти клавиатурой tabs, group picker, accordion, cells, dropdown и tooltip trigger.
2. Проверить доступные имена, роли, состояние `aria-expanded`, `aria-selected` и отсутствие захвата фокуса скрытыми элементами.
3. Проверить контраст сплошных и штриховых состояний и убедиться, что текущая/предыдущая недели различаются одной/двумя угловыми точками без зависимости только от цвета.
4. Проверить desktop viewports 1440, 1280 и 1024 px; меньшие размеры фиксировать как исследование, если мобильный контракт ещё не утверждён.

### Этап E. Автоматические команды

Из корня workspace:

```powershell
npm.cmd run check
```

Дополнительно:

```powershell
cd s-center-prototype
npm.cmd run check

cd ..\component-library-transfer
npm.cmd run verify
npm.cmd run build
```

### Этап F. Итоговый отчёт

Отчёт должен содержать:

- сводку `PASS / FAIL / BLOCKED / NEEDS DECISION`;
- замечания с приоритетом и точными файлами/строками;
- browser screenshots только для значимых состояний;
- перечень непроведённых проверок с причиной;
- отделение дефекта реализации от отсутствующего продуктового или backend-контракта;
- решение, можно ли закрыть каждый пункт follow-up плана.

## 5. Критические сценарии приёмки

Аудит считается успешным только если одновременно выполнены следующие условия:

- ни один уровень дерева выше объекта не показывает данные произвольного дома;
- нижняя массовая панель не является способом ввода статуса в MVP;
- все пять семантик визуально и текстово различимы;
- отсутствующая геометрия не выглядит как доступная ячейка без работ;
- свёрнутый список позволяет найти актуальную работу по датам и готовности;
- tooltip истории содержит четыре обязательных поля и не заявляет реальное сохранение там, где его нет;
- общие компоненты проверены в Storybook, а продуктовые правила остались в feature-слое;
- корневая проверка и компонентная сборка завершились без ошибок либо ограничения явно зарегистрированы.
