# Адаптация в другом проекте

## 1. Инвентаризация проекта-получателя

Перед интеграцией определить:

- frontend-стек и сборщик;
- существующие токены, reset и глобальную типографику;
- уже имеющиеся компоненты с той же ролью;
- правила импорта CSS и статических ресурсов;
- accessibility- и browser-требования;
- допустимость vanilla DOM-компонентов в выбранной архитектуре.

Не заменять существующие компоненты только из-за совпадения названия. Сначала сопоставить их публичный контракт, состояния, пользовательский результат и потребителей.

## 2. Проверка снимка

1. Выполнить `npm install` внутри перенесённой папки.
2. Выполнить `npm run verify` для проверки локальности относительных зависимостей.
3. Выполнить `npm run build-storybook`.
4. Просмотреть состояния всех компонентов, которые планируется подключить.
5. Зафиксировать компоненты, требующие изменения токенов, API или продуктовых текстов.

## 3. Токены и стили

Сначала сопоставить `src/styles/base/tokens.css` с токенами проекта-получателя. Затем определить один из вариантов:

- сохранить токены снимка в изолированной области;
- сопоставить переменные с действующей дизайн-системой;
- заменить значения без переименования публичных переменных;
- переименовать переменные и механически обновить потребителей внутри пакета.

Не подключать одновременно несколько глобальных reset-правил без проверки каскада. `core-ui.css`, `component-library.css` и `drawers-filters-actions.css` могут содержать правила, которые в новом проекте следует дополнительно ограничить корнем дизайн-системы.

## 4. Компоненты и продуктовая логика

Общая база хранит структуру и локальное UI-состояние. Проект-получатель должен владеть:

- данными и загрузкой данных;
- фильтрацией, поиском и сортировкой;
- правами и условиями доступности;
- сохранением и серверными операциями;
- текстами, зависящими от бизнес-сценария;
- результатами действий и обработкой ошибок.

Поля `consumers` в `registry.js` описывают исходный S-Tracker. При адаптации их нужно заменить фактическими областями проекта-получателя либо очистить.

## 5. Стратегия интеграции

Рекомендуемый порядок:

1. Подключить пакет без замены существующих интерфейсов.
2. Согласовать токены и визуально проверить Storybook.
3. Выбрать один простой компонент и заменить одного потребителя.
4. Проверить видимый результат, клавиатурное управление и ошибки консоли.
5. Переносить следующие компоненты небольшими группами.
6. Удалять прежнюю локальную реализацию только после проверки всех её потребителей.

Если проект-получатель использует React, Vue или другой декларативный frontend-стек, не вставлять DOM-фабрики непосредственно в дерево framework. Сначала выбрать архитектуру адаптера или переписать компоненты с сохранением визуальных и интерактивных контрактов Storybook.

## 6. Завершение адаптации

Адаптация считается завершённой, когда:

- Storybook собирается внутри проекта-получателя;
- относительные ресурсы разрешаются без обращения к S-Tracker;
- компоненты используют токены проекта-получателя;
- реестр отражает фактических потребителей;
- выбранные интерфейсы используют одну реализацию каждого общего компонента;
- сборка, accessibility-проверка и связанные пользовательские сценарии проходят;
- временная переносимая копия либо становится официальным пакетом проекта, либо удаляется после переноса исходников в постоянное место.
